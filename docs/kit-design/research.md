# Кит epic: исследование подходов и коррективы по эпику Docker

Входные данные: ваше видение (ответ на #6566), `docs/brief.md`, `journal/docker-install.md` (наблюдения 1–23), код LADO 0.40.0 и sdlc 0.5.0, обзор открытых источников (ссылки в конце).

## 1. Ваше видение, разложенное на требования

| # | Требование (вашими словами) |
|---|---|
| V1 | Постановка фичи в свободной форме, от одной строки до ТЗ. Кит оценивает, насколько она проработана, и задаёт вопросы **до** разработки. |
| V2 | Если данных хватает, фича разбивается на 1..N задач (бывает и одна). Нужно решить, что делать с граничными случаями. |
| V3 | Каждая задача регистрируется в трекере через абстракцию `tracker`, без привязки к конкретному трекеру. |
| V4 | Каждая задача стартует с чистого листа: новая сессия sdlc с этим китом, обычный flow `task`. |
| V5 | Больше автономии, но контроль над решениями остаётся. Вопросы и гейты сессий-задач идут супервизору эпика, а не человеку. Вопросы могут приходить от нескольких сессий сразу. |
| V6 | Человек говорит только с супервизором эпика. Тот общается на уровне выше и рекомендует обоснованные решения. |
| V7 | Сессии двигают задачи в трекере и сливают свои ветки как обычно. Вопрос: какая ветка основная, `main` или ветка эпика. |
| V8 | Супервизор эпика следит за всеми сессиями, определяет порядок слияний, проверяет и решает конфликты. |
| V9 | Итог — готовое решение и аргументированный отчёт по всем принятым решениям. |
| V10 | Слияние фичи в основную ветку делает человек. До этого отдельный агент проверяет итог, решает конфликты и готовит сдачу. |
| V11 | Прежде чем строить кит, доработать ядро LADO, если без этого не обойтись. |

## 2. Что делают другие

| Подход | Суть | Что взять | Чего там нет |
|---|---|---|---|
| **AWS AI-DLC** (Inception → Construction → Operations) | Inception превращает намерение в требования, истории и «units of work» с зависимостями. Команда проверяет вопросы ИИ на «Mob Elaboration». Construction крутит цикл по каждому unit. Глубина процесса подстраивается под задачу. Журнал всех решений ведётся. | Фаза Inception = V1–V2. Адаптивная глубина: маленькая фича идёт одной задачей. Аудиторский журнал решений = V9. | Параллельных сессий и делегирования гейтов нет: человек участвует синхронно, «мобом». |
| **Spec-driven** (GitHub Spec Kit, Kiro, BMAD, OpenSpec) | constitution → specify → plan → tasks → implement. Kiro даёт режимы от supervised до autopilot. BMAD «шардирует» PRD на эпики и истории. | Спецификация фичи как источник задач. «Steering»-файлы с правилами в каждом запуске = наши правила брифа. | Работают на уровне одной фичи в одной сессии. Задачи выполняются по очереди одним агентом, оркестрации независимых сессий нет. |
| **Devin «manages Devins»** | Координатор делит большую задачу, раздаёт дочерним сессиям (каждой чистый VM), следит, шлёт поправки посреди работы, решает конфликты, собирает результат. Довод Cognition: одна сессия, которая берёт слишком много, теряет фокус. | Ближе всего к V4+V8. Наш опыт тот же: контекст супервизора эпика терялся (набл. 13, 20). | Гейтов человека внутри дочерних сессий нет. Решения принимает координатор, и как их аудитировать, не описано. |
| **Claude Code agent teams, Anthropic multi-agent research** | Lead + teammates со своим контекстом, общий список задач с зависимостями, почтовый ящик. Лид одобряет план teammate до кода. | Одобрение плана лидом **до** кода = делегированный гейт дизайна (V5). Совет «3–5 исполнителей». Anthropic: мультиагентность плохо подходит, когда у задач много взаимозависимостей, а это наш случай для кода. | Одна машина и одна сессия. Трекера и ветки слияния нет. |
| **Gas Town (Yegge)** | «Mayor» раздаёт работу в «convoys» десяткам агентов, «Refinery» отвечает за слияния, состояние работы лежит в git (Beads) и переживает падение сессий. | Отдельная роль слияния = V8/V10. Состояние эпика в файле, а не в контексте (наше набл. 13–15, 20). | По словам автора, альфа: «не используйте всерьёз». Контроль человека слабый. |
| **Слияние при параллельных агентах** (trunk-based/DORA, merge queues, stacked PRs) | Короткие ветки в trunk, незаконченное прячется («dark», флаги). Stack — только для действительно последовательной работы. Очередь слияний нужна, потому что два «зелёных» PR вместе ломают main (логический конфликт). Сливать по одному и подтягивать остальные. | Ответ на V7–V8 (см. §4.4). | — |

**Общие выводы из источников:**
1. **Узкое место — проверка, а не генерация.** «Не запускайте больше агентов, чем можете осмысленно проверить» (Osmani). Ориентир — 3–5 параллельных исполнителей.
2. **Параллельно — только непересекающиеся задачи** («один файл — один владелец»). Остальное идёт по очереди или волнами по графу зависимостей.
3. **План дешевле кода.** Самый выгодный контроль — одобрение дизайна до кода.
4. **Автономия задаётся границами:** агент действует сам внутри рамки и останавливается на её краю (CSA, arXiv 2506.12469). Anthropic измерил, что Claude Code сам чаще останавливается спросить, чем человек его прерывает. Источники предупреждают о «level-skipping»: человек формально «ревьюит», а на деле не смотрит.
5. **Делегировать вопросы дочерних сессий координатору с возможностью эскалации к человеку не умеет никто из найденных.** Devin шлёт поправки, Claude teams пересылают план лиду, но гейта с аудитом и подъёмом к человеку нет ни у кого. Это и есть ниша, которую вы описали.

## 4. Предложения по главным вопросам

### 4.1. Готовность постановки (V1)
Отдельный первый шаг кита. Супервизор эпика оценивает постановку по чек-листу тем: цель и «готово», пользователи, границы, данные и миграции, секреты, обновление и откат, платформы, наблюдаемость, тесты. Выдаёт уровень «хватает / не хватает / нужно исследование» и вопросы раундами. Если нужно исследование, оно идёт задачей sdlc, как LAD-52. Это совпадает с Inception у AI-DLC.

### 4.2. Разбиение (V2) и граничные условия
- Малая фича → одна задача, эпик только сопровождает (адаптивная глубина как у AI-DLC).
- Большая → план из шагов, у каждого проверка. Первым идёт «ходячий скелет». Шаги, не пересекающиеся по файлам, разрешены параллельно, но не больше K одновременно (предлагаю 2–3: больше вы не проверите).
- Граничные условия: у каждого шага есть рамка и список «вне рамки → в «Потом» плана или в отдельную задачу derived».

### 4.3. Автономия и гейты (V5, V6): «делегированный одобряющий»
Предлагаю уровни на каждый гейт sdlc в сессии-задаче. Они задаются в плане эпика, и вы можете поменять их на любом шаге:

| Гейт sdlc | По умолчанию | Супервизор эпика решает сам, когда | Поднимает к вам, когда |
|---|---|---|---|
| вопросы аналитика | эпик отвечает | ответ есть в плане, решениях, исследовании | вопрос меняет рамку, решение не записано, задеты ваши «никогда без меня» |
| `design_ok` | эпик одобряет | дизайн в рамке шага, без новых решений | расширение рамки, новое архитектурное решение, несогласие с ревью |
| `merge_ok` | **вы** (ручная проверка) или эпик — по шагу | шаг без пользовательского пути (внутренний рефакторинг, тесты), ревью сошлось, CI зелёный | шаг меняет путь пользователя или требует ручной проверки |
| слияние фичи в основную ветку | **всегда вы** | — | — |

Каждое решение эпика за вас записывается в журнал решений с основанием. Так получается отчёт V9 и защита от «level-skipping»: вы видите, что одобрено без вас.

### 4.4. Ветка (V7, V8)
Рекомендую две стратегии, выбор при старте эпика:
- **A. «Trunk», по умолчанию** (как в Docker): каждый шаг сливается в `main` и оставляет продукт рабочим. Незаконченное спрятано: не подключено, за флагом или не описано в документации. Плюсы: нет дрейфа, соседние задачи видны сразу. Вам остаётся одно действие — «включить фичу» (релиз или флаг). Это совпадает с данными DORA и с вашим опытом.
- **B. Ветка эпика `epic/<key>-<slug>`**, когда фичу нельзя показывать частями. sdlc 0.5.0 это уже умеет: аналитик целит PR в ветку эпика, если она есть в remote, а интегратор оставляет задачу в review. Против дрейфа супервизор эпика вливает `main` в ветку эпика после каждого шага и перед каждым слиянием задачи, по одному слиянию за раз (последовательная интеграция). Финал: PR ветка эпика → `main`, его готовит агент «готовности к выпуску», сливаете вы.

Порядок слияний (V8): по одной задаче. Перед слиянием следующей она подтягивает обновлённую базу и проходит CI. Это защищает от «логических конфликтов» двух зелёных PR.

## 5. Что нужно в ядре LADO (V11)

Проверено в коде 0.40.0:
- агентам прямо запрещено отвечать на гейты: `lado answer` при `LADO_AGENT` отказывает, `cli.py:649`;
- связи «родительская — дочерняя сессия» нет;
- `start_session` копирует киты родителя (а с двумя китами-супервизорами ведёт встроенный супервизор, `kits.py:39`).

| # | Доработка | Зачем | Можно ли без неё |
|---|---|---|---|
| L1 | Связь родитель → дочерняя сессия и события дочерней (шаг flow, гейт открыт, прогон завершён, сессия остановлена) сообщениями родителю | V6, V8; набл. 4, 22 | Плохо: опрос `lado log` по слову человека |
| L2 | **Делегированный одобряющий:** гейты и вопросы `ask_human` дочерней сессии идут супервизору родителя. Он отвечает (`answer`) или поднимает к человеку. Человек видит всё и может вмешаться | V5 | Нет: сейчас это запрещено сознательно |
| L3 | `start_session` с явными китами, `--without` и, возможно, в другом репозитории | ведущий в дочерней сессии — sdlc, а не epic; эпик может вести продукт из своего репозитория | Частично: вариант A из поправки к вопросу 5 |
| L4 | Чтение состояния дочерней сессии инструментом: `flow_status`, артефакты, лог | разбор шага (набл. 2) без CLI | Да, через `lado log`/`lado artifacts` в Bash |

L1 и L2 — минимум, без которого ваш идеальный вариант не работает. L3 и L4 желательны.

## 6. Вопросы на раунд 2 (ответы зависят друг от друга мало)

1. **Порядок работ.** Сначала L1+L2 (и L3?) задачами в `ladohq/lado` через sdlc, а прогон `create/epic` держать на шаге design, пока ядро не готово? Или писать блюпринт сейчас под будущее ядро и выпустить кит после ядра? *Рекомендация:* блюпринт сейчас (он задаёт требования к ядру), ядро отдельными задачами, кит собирать после L1+L2.
2. **Гейты.** Принимаете таблицу §4.3? Особенно: `merge_ok` по умолчанию остаётся у вас при шаге с пользовательским путём. *Рекомендация:* да, ваш опыт с ручными проверками это подтверждает.
3. **Ветка.** Стратегия A по умолчанию и B по выбору на старте эпика? *Рекомендация:* да.
4. **Параллельность.** Не больше 2–3 сессий-задач одновременно, только с непересекающимися файлами? *Рекомендация:* 2 для начала.
