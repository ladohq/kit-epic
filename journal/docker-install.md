# Журнал эпика: установка LADO через Docker

Эпик: дать пользователю запускать и полноценно использовать LADO через Docker.
Основа: исследование LAD-52 (`ladohq/lado`, `docs/research/docker-install.md`).
План: `docs/research/docker-install-plan.md`, там же.
Ведёт: супервизор сессии LADO `lad-52` (кит sdlc). Каждый шаг выполняется отдельной сессией LADO с flow `task` кита sdlc.

Журнал нужен для нового кита, который будет вести эпик от начала до конца автоматически или полуавтоматически. Здесь записано, как мы это делаем руками: что сработало, что нет, где нужен человек.

## Цикл, как он сложился

1. **Исследование** — отдельная задача (LAD-52), результат — документ с проверками H1–H9 и трудностями 5.1–5.16.
2. **Ревью исследования и план.** Ревью: что хорошо, пробелы, противоречия. План: задачи-шаги, у каждого шага есть проверка. Цель — маленькие проверяемые шаги и как можно раньше «ходячий скелет» в CI. Человек принимает решения по открытым вопросам (таблица «Принятые решения»).
3. **Правила ведения** (решения человека):
   - план лежит в репозитории рядом с исследованием;
   - в трекере создаётся только очередная задача;
   - после каждого шага план пересматривается;
   - эпика-ветки нет, всё сливается в `main`.
4. **Шаг:**
   - черновик задачи (артефакт);
   - «да» человека;
   - задача в трекере (метка проекта);
   - бриф (артефакт);
   - вопрос «Start session <name>»;
   - `start_session`;
   - сессия проходит flow `task`: аналитик → гейт дизайна → разработчик → ревью → гейт слияния → интегратор.
5. **После шага:**
   - человек пишет «задача закончена»;
   - супервизор собирает итоги;
   - предлагает правки плана и черновик следующей задачи;
   - «да» человека;
   - задача в трекере и PR с правкой плана (`main` защищён);
   - CI;
   - слияние;
   - новая сессия.

## Шаги

### Т1 — LAD-59: признак «LADO в контейнере», запрет `lado update` (S)

- **Итог:** PR #40. `LADO_CONTAINER`, отказ `lado update` в контейнере, «in a container» в doctor.
- **Из «Not checked»:** агенты не видят `LADO_CONTAINER` из `ENV` образа, потому что их окружение берётся из login shell.
  - **Правка плана:** в Т3 добавлено «ставить его ещё и в `/etc/profile.d`».
  - Пример: хвост одного шага становится требованием будущего шага.
- **Процесс:**
  - супервизор заявил, что `main` не защищена. Классический API защиты веток вернул 404, а rulesets он не проверил. Человек переспросил, после этого план правили через PR.
  - **Урок для кита:** проверять rulesets (`gh api repos/<o>/<r>/rules/branches/<b>`), а не только branch protection.
- **Процесс:**
  - текст выбора «Влей PR #42 после CI и Start session lad-63» не прошёл бы строгую проверку `start_session`, пришлось спрашивать ещё раз.
  - **Урок:** выбор «Start session <name>» всегда отдельной кнопкой и ровно в такой форме.
- **Процесс:** супервизор без спроса связал задачи в трекере. **Урок:** в трекер — только то, о чём попросили.

### Т2 — LAD-63: ссылки и предупреждение UI-сервера в контейнере (S)

- **Итог:** PR #45. Новая переменная `LADO_REPOS` — папка репозиториев, работает и без Docker.
- **Из ревью:** внешний ревьюер нашёл, что при сервере на loopback ссылка с хоста не откроется. Находку отклонили как задачу образа.
  - **Правка плана:** в Т3 «сервер на `0.0.0.0`».
- **Человек:** спросил, не помешает ли правило «порт на хосте = порт в контейнере» будущему менеджеру контейнеров.
  - **Ответ:** порт — одна переменная compose `LADO_PORT`, у каждого контейнера свой номер.
  - **Правки плана:** Т3 уточнена, в «Потом» добавлен менеджер контейнеров.
  - **Урок:** при пересмотре плана человек приносит планы на будущее, и шаг надо проверять на совместимость с ними.
- **Параллельно:** CI изменился (LAD-60, единственная обязательная проверка — `ci-ok`). Это пришлось внести в Т3.
  - **Урок:** при разборе смотреть не только свою задачу, но и что ещё влилось в `main`.

### Т3 — LAD-64: образ в репозитории, сборка и smoke в CI (M)

- **Итог:** PR #50:
  - `docker/` (Dockerfile, compose);
  - образ стартует одной командой `docker run` без файлов;
  - новый слой тестов container;

  - **Урок:** ручная проверка человека нигде не фиксируется. Киту нужно место для неё, например комментарий в задаче или запись в журнале.
- **Правка плана:** объединить Т4 и Т5.
  - **Почему:** тест Т4 (коммит воркера в папку хоста) на Linux-раннере CI (uid 1001, а в образе uid 1000) упал бы на проблеме Т5.

- **Решение человека из LAD-64:** образ должен запускаться одной командой без файлов. Как это показывать в документации, решаем в Т7/Т8.

### Т4 (+Т5) — LAD-69: папка проектов по пути хоста и владелец файлов (M)

- **Итог:** PR #56:
  - `entrypoint.sh`: разовый переход в root, смена uid, `setpriv`;
  - 10 тестов слоя container.
- **Ревью:**
  - 3 важные находки (F1, F4, F10);
  - F4 и F10 — один класс: «старт падает при ужесточённых настройках контейнера», и внесли их сами исправления ревью;
  - 2 из 2 внешних раундов.
- **Процесс:**
  - человек отклонил слияние: «дай точные инструкции как проверить руками на Mac»;
  - ревьюер написал 10 шагов;
  - человек проходил их час с помощью супервизора сессии.

  Ошибки:
  - образ собран из `main`, а не из ветки PR;
  - compose запущен не из `docker/`;
  - `LADO_PROJECTS` задан в другом терминале;
  - имя сессии по умолчанию не совпало с инструкцией;
  - `~` в поле UI внутри контейнера — это `/home/lado`.

  **Уроки:**
  - инструкция для ручной проверки должна быть частью PR с самого начала, а не по отказу;
  - в инструкции надо прямо писать «переключись на ветку», «из какой папки», «какое имя будет у сессии»;
  - трудности ручной проверки — это трудности будущего пользователя, и они попадают в план (Т8, Т14).
- **Процесс:** ревьюер выполнил `docker volume prune -f` на машине человека — разрушительная команда вне репозитория.
  - **Урок для кита и для sdlc:** роли запрещены глобальные разрушительные команды Docker и системы. Только свои контейнеры и тома, по имени.
- **Правка плана:** Т6 разбить на Т6а и Т6б.
  - **Почему:** миграция базы с бэкапом — блокер перед публикацией и маленький шаг; остановка и возобновление сессий — удобство, его надо проектировать.
  - **Приём:** разбивать, когда части независимы и одна из них блокирует дальнейшие шаги.
- **Выводы разнесены по будущим задачам:**
  - Т8 — одна команда запуска, предупреждение о папке вне `LADO_REPOS`;
  - Т9 — инструменты в домашнем томе, а не в `/opt`;
  - Т11 — настоящий Linux, rootless Docker, Podman.
- **Побочное:** найден флейк UI-теста, по слову человека заведена задача LAD-72. Вопрос интегратора закрылся вместе с ним, ответ пришлось собирать заново через супервизора.
  - **Урок:** находку «не по эпику» супервизор эпика должен подхватить сам.

### Т6а — LAD-71: новый образ на старом томе, миграция базы с бэкапом (S)

- **Итог:** PR #58.
  - Бэкап перед *любой* миграцией базы (`state.migrate`), а не только в контейнере. Аналитик предложил обобщить: одно правило в ядре. Человек согласился со всеми четырьмя рекомендациями сразу.
  - Обновление в контейнере — два шага, с `lado:previous`.
- **Масштаб:** аналитик выбрал tweak, хотя план называл S. Проектирование заняло один вопрос из четырёх пунктов.
- **Процесс: задержка на гейте слияния.**
  - Человек отклонил слияние словами «Мой пункт с ворот дизайна закрыт не до конца». На деле это была цитата из рекомендации супервизора сессии.
  - Разработчик искал пункт среди своих кандидатов и ждал. Пояснение супервизора дошло до него не сразу.
  - Человек спросил: «процесс затянулся. Все в порядке?».

  **Уроки:**
  - если отказ ссылается на рекомендацию или прошлый пункт, супервизор сразу передаёт работнику этот пункт целиком;
  - на долгом шаге человек хочет короткий отчёт о ходе, не дожидаясь вопроса.
- **Находка гейта от человека** (M1, важная): после `docker compose pull` у прежнего образа нет имени. Её исправление (`lado:previous`) породило новую находку ревью G3: одна правда в двух местах, подсказка LADO и шапка compose. Её закрыли тестом на равенство.
- **Хвосты, отложенные до Т7:**
  - `lado:previous` — одно имя на машину (G2). Это противоречит плану человека про менеджер контейнеров;
  - устаревшая фикстура (H2).

  Супервизор сессии перечислил оба хвоста в итоговом сообщении человеку и попросил передать их супервизору эпика.
  - **Урок:** итоговое сообщение супервизора сессии — ещё один источник для разбора. Человек прямо проверил, учтены ли эти хвосты.
- **Правка плана:** поменять порядок, Т7 раньше Т6б.

  - **Приём:** переставить шаги, когда блокер снят, а у следующего по плану шага ценность ниже, чем у шага после него.
  - Хвост G2 решается не заплаткой, а сменой подхода в Т7 (теги версий вместо `lado:previous`).

### Т7 — LAD-73: образ в GHCR при релизе, все четыре CLI, обновление по тегу версии (S/M)

- **Итог:** PR #61.
  - Release workflow собирает образ из wheel релиза, гоняет тесты слоя container на amd64 и arm64, пушит по digest и ставит теги.
  - `lado:previous` убран. Обновление — новый `LADO_VERSION` в `.env`, откат — прежний.
  - В контейнере LADO не называет команд обновления. Это решение человека на гейте дизайна: команды даст документация.
- **Решение человека посреди шага (до запуска сессии):** один образ со всеми четырьмя CLI. В бриф ушло условие выхода: «если замедлит — вынести в отдельную задачу». Разработчик измерил и подтвердил, что порог не превышен: образ 615 MB против 2,5 GB у прототипа, сборка 99 с.
  - **Урок:** решение с условием («добавим, если не замедлит») формулировать в брифе как проверяемый порог. Тогда работник сам решает и отчитывается цифрами.
- **Главная проверка шага возможна только после него:** Release workflow запускается только на теге. Шаг слит с открытыми проверками до первого RC, а одну из них делает человек руками: сделать пакет GHCR публичным.
  - **Урок:** у шага может быть «проверка после слияния». Плану нужен статус «сделан, проверка открыта до события X», а киту — напоминание при событии X (релиз).
- **Ручная проверка снова споткнулась о переменные окружения,** оставшиеся в shell от прошлого теста. Так было уже в LAD-69. Человек разобрался сам, супервизор сессии помог диагнозом по скриншоту.
  - **Урок:** повтор одной и той же ловушки — довод в план продукта (Т8, Т14). Кит должен замечать повторы между шагами: это работа журнала.
  - Супервизор сессии не видел Docker человека (другой контекст или демон). Ручная проверка идёт на машине человека, и супервизор её не наблюдает.
- **Вопрос человека после шага:** «Когда мне можно будет выпустить новый релиз?» Релиз как точка проверки шагов — часть цикла эпика: план должен знать, какие шаги ждут релиза.
- **Правка плана (PR #62):**
  - Т7 сделана, проверки открыты до 0.39.0rc1;
  - реальный размер образа в решениях;
  - Т1 уточнена;
  - в Т8 и Т14 перенесено, чему научила LAD-73.

  Порядок не менялся.
  - **Приём:** сверять цифры решений (размер, время) с измеренными и править раздел решений.

### Т6б — LAD-74: сессии останавливаются и возобновляются вместе с контейнером (M)

- **Итог:** PR #65, войдёт в 0.40.0, схема 29.
  - На SIGTERM сессии помечаются остановленными с отметкой «возобновить при старте».
  - При старте контейнера сначала миграция, потом возобновление. Так же после `docker kill`.
  - Работников запускает супервизор.
- **Решения человека:** все пять рекомендаций аналитика приняты одним ответом. Шаблон «вопросы с рекомендацией и альтернативой» снова сработал за один круг.
- **Релиз посреди шага.** 0.39.0 вышел, пока PR ждал гейта слияния. Человек отклонил слияние: «Вышел новый релиз. Давай подтянем изменения».
  - Разработчик влил main и перенёс строку CHANGELOG из выпущенной версии в новую. Git сам оставил её в выпущенном разделе, без конфликта.
  - Бриф заранее предупреждал, что строка CHANGELOG идёт под версию, открытую в main на момент слияния. Это помогло.
  - **Урок:** при релизе посреди шага кит сам предлагает подтянуть main в открытые PR эпика и проверить, под какой версией лежит строка CHANGELOG.
- **Хвосты:**
  - ручная проверка на Mac и live-тесты уходят в RC 0.40.0: обновление образа 0.39.0 → 0.40.0 проверит миграцию и возобновление разом;
  - «Возобновить все» без Docker — в «Потом»;
  - неатомарное создание `lado.db` — в BACKLOG.
- **Правка плана (PR #69):** Т6б сделана, проверки Т7 закрыты, Т10 = LAD-76, новый пункт в «Потом».
  - **Приём:** проверку, которую нельзя сделать сейчас, привязать к ближайшему событию, которое проверит её само (обновление образа на RC).
- **Человек захотел обновить систему посреди эпика** и спросил, как не потерять историю чата с супервизором эпика.
  - История сообщений лежит в `lado.db` и переживает обновление. Контекст модели супервизора не переживает.
  - Перед обновлением супервизор записал артефакт передачи дел `epic-handoff`: состояние, источники, следующий шаг, правила.
  - **Урок:** киту нужен свой файл состояния эпика, который супервизор читает при старте и возобновлении. Контекста модели для этого недостаточно.

### Т10 — LAD-76: секреты, git и логины в контейнере (M)

## Наблюдения для кита (сводка)

1. **Человек нужен в точках:**
   - решения по исследованию и плану;
   - «создать задачу»;
   - «запустить сессию»;
   - гейт дизайна;
   - гейт слияния (с ручной проверкой).

   Остальное автоматизируется:
   - сбор итогов;
   - черновик правок плана и следующей задачи;
   - PR с планом и его слияние после зелёного CI.
2. **Сбор итогов** — отдельный шаг с фиксированным набором источников (таблица выше). Самые недооценённые источники — переписка сессии с человеком и итоговое сообщение её супервизора с хвостами.
3. **Приёмы правки плана:**
   - записать результат шага;
   - перенести хвосты («Not checked», «Out of scope», отклонённые находки) в будущие шаги;
   - объединить шаги;
   - разбить шаг;
   - переставить шаги;
   - заменить заплатку сменой подхода в будущем шаге;
   - добавить пункт в «Потом»;
   - проверить шаг против планов человека на будущее.
4. **Конец шага сейчас не виден супервизору эпика.** Сессия, запущенная через `start_session`, ничего не сообщает обратно, и человек пишет «задача закончена» руками. Варианты:
   - шаги — runs flow `task` в той же сессии;
   - LADO сообщает родительской сессии о конце дочерней.
5. **План — файл в репозитории продукта, правки — через PR.** Плюс: история и ревью. Минус: на каждый шаг лишний PR и ожидание CI. Можно держать план вне продукта (в журнале или трекере) или вносить правку плана в PR самого шага.
6. **Ручная проверка человека** — первоклассный шаг: инструкция в PR с начала, место для записи результата.
7. **Связь человек ↔ работник через гейты:** отказ с цитатой должен доходить до работника развёрнутым; на долгих шагах — отчёт о ходе без вопроса.
8. **Безопасность ролей на машине человека:** никаких глобальных разрушительных команд (`docker volume prune`, `docker system prune`, `rm -rf` вне рабочих папок).
9. **Проверка после слияния:** у шага может быть проверка, возможная только на событии (релиз). Плану нужен статус «сделан, проверка открыта до X», киту — напоминание на X. Релиз — точка цикла эпика.
10. **Решение с условием** («добавим, если не замедлит») задаётся в брифе проверяемым порогом. Тогда работник решает сам и отчитывается цифрами.
11. **Повторяющиеся ловушки между шагами** (одна и та же ошибка ручной проверки) замечает журнал и превращает их в доводы для плана продукта.
12. **Супервизор эпика не трогает основной checkout человека.** Правки плана — через воркера в его worktree или хотя бы в отдельном `git worktree add`, а не `git switch` в основной копии (замечание человека 2026-10-15 после PR #62).
13. **Файл состояния эпика.** Контекст супервизора теряется при обновлении или возобновлении. Состояние эпика держать в артефакте или файле, который супервизор читает при старте: шаг, сессии, открытые проверки, правила человека.
14. **Релиз между шагами:** подтянуть main в открытые PR, проверить версию в CHANGELOG, перенести проверки «после слияния» в чек-лист релиза.
15. **Файл состояния эпика работает.** После возобновления сессии lad-52 с потерей контекста супервизор по одному артефакту `epic-handoff` дошёл до запуска следующей сессии: прочитал передачу, черновик задачи, образец брифа, сверил задачу в трекере. Человеку хватило одной фразы «прочитай epic-handoff и продолжай».
16. **Граница шага в дизайне.** Аналитик шага эпика держит рамку шага из плана и на каждом расширении спрашивает: «шаг или новая задача?». Без этого дизайн LAD-76 разросся до профилей за 10 раундов, и вернул его человек.
17. **Задачи, родившиеся в шаге,** заводит сама сессия по «да» человека, со связью derived и артефактами дизайна. Супервизор эпика вписывает их в план. Бриф явно говорит, что план и журнал ведёт эпик.

18. **Шаг «готовность к выпуску» перед релизом эпика:** свести итоги всех шагов и проверить обновление с прошлой версии со старыми файлами пользователя. Отдельные шаги проверяют только чистую установку.
19. **Чек-лист релиза — часть плана эпика.** Шаг, который меняет путь пользователя, сверяется с ручными проверками релиза в том же цикле.

20. **Файл состояния эпика должен читаться сам.** 2026-10-17 сессия lad-52 возобновилась после обновления LADO, и человек сразу написал «LAD-87, потом Т9, параллельно» — без «прочитай epic-handoff». Супервизор начал по умолчанию кита: запустил прогон `task` в своей сессии и искал «Т9» в трекере. Человек остановил: «ты не помнишь, о чём мы говорили». Контекст восстановлен по `lado log` и артефактам `epic-handoff` и `docker-remaining`, прогон отменён без следов. Вывод для кита: супервизор эпика при старте и возобновлении сам читает файл состояния эпика, а не ждёт ссылки на него. Номера шагов плана (Т9) и ключи трекера — разные пространства; черновой шаг без задачи супервизор узнаёт по плану.

21. **Эпик видит только свои шаги, а продукт меняется и рядом.** Задачи вне эпика (LAD-94) меняют то, на чём стоят шаги эпика (`compose.yaml`). Разбор шага должен смотреть `git log` main с прошлого разбора, а не только PR своих шагов.
22. **Хвосты сессии приходят к человеку, а не к эпику.** Сессия-шаг пишет «хвосты для плана» человеку, а эпик их читает в `lado log <сессия>`. Это работает, но держится на том, что человек скажет «слито». Нужен канал «сессия-шаг → эпик».
23. **Человек может не взять совет эпика** (LAD-90 до релиза) и выбрать релиз. Тогда эпик переносит риск в чек-лист релиза (строка CHANGELOG, ручная проверка обновления со старым файлом), а не спорит.
